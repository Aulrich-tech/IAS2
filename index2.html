Web Services & the 3 API Styles

Web Service

A defined method for facilitating communication and interoperability between different software systems over a network, delivered via the Web.

Built on open standards: XML, SOAP, and HTTP.

Website vs. Web Service

  • Requester — a browser asks (website) vs. a program asks (web service).
  • Response — HTML for a human vs. XML/JSON for another program.
SOAP — Simple Object Access Protocol1

A communications protocol that lets web services exchange structured data, based on XML, with a consistent request/response structure. Platform and language independent, so it's the natural fit for integrating systems built on different tech stacks. Most often rides on HTTP, but can also use SMTP or TCP. Book's example: a weather service that accepts a SOAP request with a location and returns an XML forecast.

REST — Representational State Transfer2

An architectural style, not a protocol — it just uses HTTP's existing features. Emphasizes stateless client-server communication and drives actions on resources with the HTTP verbs GET, POST, PUT, DELETE. Usually exchanges lightweight JSON. Book's example: an e-commerce API for retrieving products, adding to cart, and placing orders.

GraphQL3

A query language for APIs plus a runtime for executing those queries. Clients ask for exactly the data they need — cutting both over-fetching and under-fetching — and the server responds in JSON shaped the way the client asked. Book's example: a social media API returning a profile, posts, and related data in one round trip.

03

Synchronous vs. Asynchronous

Synchronous

  • The sender waits for a response
  • Like a phone call — both parties must be free at once
  • SOAP, REST, GraphQL
  • If the receiver is down, the request fails
↔

Asynchronous

  • The sender carries on immediately
  • Like a courier — drop it off and leave
  • MOM, message queues
  • If the receiver is down, the message waits in the queue

The test question: what happens in each case if the receiving system is down? That difference is the whole reason message queues exist.

04

Message-Oriented Middleware & Message Queuing

MOM

A software architecture that makes it easier for applications to communicate by exchanging messages. It provides a messaging backbone that manages delivery, routing, and transformation, abstracting the underlying protocol.

The Key Guarantee

MOM delivers messages even if sender and receiver are never online at the same moment, or the network or a system has problems.

Message queuing (MQ)

A core service MOM provides: storing messages in queues and managing them until the intended receiver consumes them, asynchronously.

4 benefits of message queues

1Asynchronous communication
2Reliable delivery
3Load balancing
4Fault tolerance

4 examples

Enterprise messaging1

Integrating many applications, systems, or departments — e.g. a bank's core system, payment gateway, and CRM all communicating through queues.

Order processing2

An e-commerce order is added to a queue; inventory, shipping, and billing each consume from it and complete their jobs.

Event-driven architecture3

MOM and MQ are essential building blocks for EDA — systems post events to a queue, and interested consumers subscribe.

Internet of Things4

Sensors publish messages to queues; backend systems ingest them to assess, analyze, and trigger real-time actions.

05

Service-Oriented Architecture (SOA)

Architecture that treats services as reusable components to enable interoperability and flexibility in system integration — encouraging loose coupling, modularity, and reusability through clearly articulated interfaces.

5 principles

Service Reusability1

Services encapsulate a functionality so it can be accessed by many consumers, encouraging code sharing and reducing duplication.

Service Discoverability2

Achieved through service registries and directories, so clients can locate services, learn their capabilities, and how to engage with them.

Service Loose Coupling3

Standardized interfaces (HTTP, message systems) reduce dependencies, so services can be developed, updated, and deployed independently.

Service Interoperability4

Emphasis on open standards (XML, SOAP, REST, WSDL) so services on different technologies and platforms can still communicate.

Service Composability5

Services are orchestrated or choreographed into more intricate business processes to accomplish specific goals.

4 examples

SystemBuilt from these services
E-commerceProduct catalog, inventory, payment processing, order fulfillment
BankingAccount administration, transaction processing, fraud detection, CRM
Travel bookingFlight reservations, hotel bookings, car rentals, payment processing
GovernmentSocial welfare management, online tax filing, permits & licenses, public transit
06

Event-Driven Architecture (EDA)

SOA

  • Request-driven
  • Something calls a service and asks it to do work
vs

EDA

  • Event-driven
  • Something announces a thing happened; whoever cares reacts

5 principles

Event Producers1

Components that produce events when a predetermined trigger or condition is met — internal or external changes.

Event Consumers2

Subscribe to events they care about, then act, decide, or start further processes.

Event Channels3

Carry events from producers to consumers — message queues, pub/sub systems, and event streaming platforms.

Event Processing4

Handles events and decides the relevant action, in real time or batch depending on requirements.

Event-Driven Middleware5

Event routers, brokers, and processing engines that make event routing, filtering, and processing possible.

Memory hook: producer announces → channel carries it → consumer reacts → processing decides → middleware makes it all work.

5 examples

Internet of Things

Sensor/device events trigger real-time actions like smart-home adjustments or alerts.

Financial Trading

Price changes, executions, or cancellations let traders react and manage risk in real time.

Logistics & Supply Chain

Inventory changes and shipment events enable real-time visibility and automated reactions.

Social Media & Notifications

Interactions and status changes drive notifications, feed updates, and personalization.

Distributed System Integration

Events act as integration points between distributed systems and microservices.

07

Microservices Architecture

Organizes an application as a collection of small, independent services, each geared toward one business capability and independently developed, deployed, and scaled.

Monolith

  • One application, one database
  • One change means redeploying everything
  • One crash brings the whole thing down
vs

Microservices

  • Many small services, each with its own data store
  • One change means redeploying one service
  • One crash takes out one feature

5 principles

Service Independence1

Each service handles one business capability and can be built and deployed independently, so teams can work in parallel.

Single Responsibility2

Each microservice owns one clearly specified capability with a well-defined interface to talk to others.

Loose Coupling3

Services talk via lightweight protocols (HTTP/REST, messaging), with few dependencies, so each can evolve and scale on its own.

Independent Data Management4

Each service owns its own database. Prevents a single centralized database from forming and stops one service's schema change from breaking another.

Resilience & Fault Isolation5

Built to withstand disruptions — one failing service shouldn't be allowed to take down the whole system.

Benefits

  • Scalability
  • Agility
  • Fault tolerance
  • Independent development & deployment
  • Improved team autonomy
↔

Difficulties

  • Managing communication between services
  • Ensuring data consistency
  • Complexities of distributed systems

Integration Platforms & Tools

Integration Platform

An all-inclusive environment for planning, executing, and managing integrations — typically data translation, routing, message queuing, monitoring, and security.

Integration Tool

A standalone product that concentrates on one particular integration feature or use case.

4 integration platforms

MuleSoft AnypointCentralized API development, app connection, and org-wide data integration via GUI, pre-built connectors, and integration patterns.
IBM Integration BusFormerly WebSphere Message Broker. Enterprise messaging, transformation, and connectivity across many protocols and systems.
Dell BoomiCloud-hosted, GUI-driven; covers application, data, and B2B integration for hybrid environments.
Apache KafkaFault-tolerant, high-throughput event streaming platform — used for EDA, microservice communication, and real-time data with pub/sub and scalable queuing.

4 integration tools

Apache CamelFree, open-source framework applying enterprise integration patterns, with broad connector and data-transformation support.
PostmanAPI development and testing tool with a GUI for building, managing, and running API requests, plus collaboration and automation.
ZapierNo-code, cloud-based automation linking web apps via "Zaps" triggered by events.
JitterbitGUI platform for designing, deploying, and managing integrations, with connectors for cloud, on-prem, and databases, plus data mapping.
Correction to note The book states Postman "was created by the company Postgres." That's wrong — Postman is a product of Postman Inc., founded by Abhinav Asthana, and started as a browser extension for API testing. PostgreSQL ("Postgres") is an unrelated open-source relational database. If this comes up on an exam, the intended answer is that Postman is an API development and testing tool — don't repeat the faulty attribution.
